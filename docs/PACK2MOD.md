# risen-pack2mod: converting a Risen mod's archives into a mod for this layer

`risen-pack2mod.exe` reads the packed archives of a Risen mod (the classic `.pNN` patch volumes and `.pak` files, container `G3V0`), compares them with **your own copy of the game's archives** and writes a normal mod for this layer: loose resource files, generated Lua data that stacks with other mods (through `risen.template`, `risen.balance`, `risen.dialog`, `risen.entity`), string files and a report that lists everything it could not convert.

Why: a mod that ships `.p00`/`.p01`/`.p02` volumes replaces whole template files (and with them everything other mods patched), cannot be combined with another such mod, is not savegame-safe when it changes, and needs a 32-bit-era install. The converted form carries only the differences, is applied at run time, and can be switched on and off in the Mods tab. See [EXTENDED_MOD_ANALYSIS.md](EXTENDED_MOD_ANALYSIS.md) for the analysis that led here.

**Licensing.** The repository ships only the converter. The output contains the work of the mod's author (numbers, texts, item and recipe design, meshes, textures, actors): it is a derived work, for private use on your own machine. **Do not commit it, do not redistribute it** (not even a "numbers only" extract) without the author's permission. The tool writes a `.gitignore` (`*`) and a `NOTICE.txt` into every output folder; `mods/_generated/` and `mods/risen_extended/` are git-ignored in this repository. The tool reads the mod as data (nothing in it is executed) and never writes to the game directory.

## Usage

```powershell
risen-pack2mod <mod folder | archive files...> --baseline <Risen data dir> --out <mods\name> [options]

risen-pack2mod C:\Mods\MyMod --baseline 'C:\...\Risen\data' --out 'C:\...\Risen\bin\spass\mods\my_mod' --id my_mod
risen-pack2mod C:\Mods\MyMod\common\templates.p00 C:\Mods\MyMod\common\templates.p01 --baseline ... --out ... --dry-run
risen-pack2mod C:\Mods\MyMod --baseline ... --list                      # every file of every archive: new / changed / same
```

| Option | Meaning |
|---|---|
| `--baseline DIR` | the Risen **data** directory of your own game (holds `common\*.pak` and `compiled\*.pak`; Risen Enhanced or the classic game; official `.pNN` volumes of the baseline are applied too). Read only. |
| `--out DIR` | the mod folder to write. The generated sub-folders (`data`, `strings`, `assets`, `assets_off`, `variants`) are replaced on a rerun, `config.lua` is kept. The tool **refuses** a non-empty folder it did not create (no `manifest.json`) and any folder inside the game's data directory. |
| `--id ID`, `--name TEXT` | mod id (default: made from the folder name) and display name |
| `--combat changelog\|shipped\|off` | which `compiled_combatspecies.bin` becomes the loose file: the oldest volume that ships one (the author's changelog state, default), the newest (what the last volume ships) or none |
| `--profile FILE` | JSON profile with knowledge about one specific mod (see Profiles) |
| `--strings all` | apply every differing string row (default: new rows and the rows of converted items) |
| `--no-assets`, `--no-world` | skip the (large) resource copy / the dialogue and world extraction |
| `--project FILE.rmk.json` | also (or instead of `--out`) write the result as a risen-modkit project, see "Editor project" |
| `--world-edits` | with `--project`: also carry the entities the mod's world layers move, remove or add (default off: they cannot be told from the classic base's own differences, see "Editor project") |
| `--verify` | with `--out` and `--project`: export the project again and compare it with the converted mod; exit 1 on a difference |
| `--report FILE` | where to write `report.md` (default `<out>\report.md`) |
| `--list` / `--dry-run` | list the archives and files and stop / analyse and print the summary, write nothing |

Input: a folder (searched recursively for `*.pNN` and `*.pak`; the parent folder name `common` or `compiled` or a baseline archive of the same name decides the kind) or archive files. Volumes are applied in number order across all base names (`.pak` first, `.p00 < .p01 < .p02`), **later wins**; files are matched by their **bare lower-case name** (the mod's volumes are usually flat, the game's keep directories; the engine finds resources by that name, RE.md section 26). Files byte-identical to the baseline are dropped.

The tool is built with the layer (`cmake --build build --config RelWithDebInfo` makes `build\RelWithDebInfo\risen-pack2mod.exe`, zlib from vcpkg) and `scripts\package.ps1` puts it next to `sentry.dll` in the release zip. It needs the Visual C++ runtime that Risen itself needs, nothing else.

## What is converted

| Mod content | Output | How the generated `main.lua` applies it |
|---|---|---|
| **Existing item templates** that differ (`GoldValue`, `DamageAmount`, `ManaCost`, requirements, effect lists, use type, category, any other scalar property whose enum / vector / string form is known) | `data/items.lua`: only the differences, entry by entry (`value`, `damage`, `mana_cost`, `requires`, `modifies`, `use_type`, `category`, `properties = { gCItem_PS = { SortValue = 400 } }`) | `risen.balance.apply` per entry; a bad entry is logged and costs only itself; on the first `tick` and again with `instances = true` on every `session.start` |
| **New item templates** | `data/new_items.lua`: `base` = the shipped item that is most like it (use type, hold type, category, property sets, scripts, then the number of differing properties), the differing numbers, `mesh`, `icon`, `material`, other properties | `risen.template.create` (savegame-safe: created again from the name at every start) |
| **Recipes** (new recipe items; shipped items that became recipes) | `data/recipes.lua`: `edit` (station, ingredients, skills, result) and `new` (a recipe item given to the player, because a shipped template cannot gain a `gCRecipe_PS` at run time) | `risen.balance` recipes / new_recipes, `risen.recipe.learn_once` |
| **Other template patches** (monster actors `eCAnimation_PS.ResourceFilePath`, projectile-like templates) | `data/patches.lua` | `risen.template.patch` |
| **String tables** (`compiled/strings/*.tab`) | `strings/all.csv` (English, the fallback for every language) and `strings/<Language>.csv`: new rows, rows of converted items (`FO_<name>`, `ITEMDESC_<name>`), spreadsheet artefacts removed (`'...'`, doubled quotes, backtick and acute for apostrophes, `-` and `...` placeholders) | the layer's `strings/*.csv` loader (`risen.loc`) |
| **Resource files** (`._xmsh`, `._ximg`, `._xmat`, `._xmac` and the other compiled `._x*` names) | flat `assets/` with the original file names; identical files skipped; replaced stock names reported | mounted at start (`mod.toml` `assets`); a loose file shadows the packed one with the same name |
| **Combat table** `compiled_combatspecies.bin` | `assets/compiled_combatspecies.bin`: **your own table** with every species whose styles, moves, fight AIs or properties differ from the mod's replaced by the mod's (the file is parsed and written back losslessly); both variants (oldest / newest volume) in `variants/` | loose file, read once at start (RE.md section 45) |
| **Weather files** (`*.g3ws`, same size as the game's) | `assets/<name>`, copy in `variants/` | loose file |
| **Dialogue** (`compiled_infos.bin`): `GiveXP` commands added to or changed on existing infos, `RunScript OnTradeInfo_RefillTradeItems` trader refills (the chapter number is read from the info's `Special_Chapter<N>` picture) | `data/dialog.lua` | `risen.dialog.get` + `add_command` / `add_script_command`; the first chapter's stock also at the start of a new game (RE.md section 44) |
| **World layers** (`*.lrent`, matched with the game's layer by file name and entity by id): items added to containers / objects / dead bodies, new items equipped by NPCs, changed `TeachSkills` limits | `data/world.lua` | `risen.entity.by_id` + `risen.item.give` / `equip`, `risen.npc.set_teach_limit`; once per savegame |

Every number, name and text comes from the archives and the enum names from the data table in `src/pack2mod/enums_data.inc` (generated by `tools/gen_pack2mod_enums.py` from `tools/extmod_enums.json`, which was learned from the engine's own reflection, docs/RE.md section 43); nothing is typed in per mod. The output is deterministic (sorted keys, no time stamps): the same inputs give byte-identical files.

Besides the data: `mod.toml`, `main.lua` and `config.lua` (switches `balance`, `new_items`, `dialogue`, `world`, `teachers`, `starter_kit`; the generic code lives in `tools/extmod_templates/` and is embedded in the tool), `features.json` (groups of loose files that `scripts\extmod-features.ps1` can switch off: one group per `--profile` asset group or `assets_new` / `assets_replaced`, `combat`, weather), `manifest.json` (counts, names, every unconverted entry with the reason, warnings), `report.md`, `NOTICE.txt`, `.gitignore`.

## What is not converted

Listed with the reason in `report.md` (and `manifest.json`: `unconverted`, `not_converted`, `warnings`, `notes`). `Needs` is `engine` (the layer has no API for it), `author` (the mod's own data is incomplete or wrong: a recipe that names a template that is in neither archive, a trader entry for a misspelled template: the tool maps a misspelling when exactly one template fits and warns), `tool` (not translated by the tool).

* **Template differences that are not data**: runtime state saved with a template (collision, rigid body, navigation, routine state, inventory snapshots, NPC state) is dropped; a property set the shipped template lacks cannot be added at run time (`engine`); new templates that are not items (NPCs, spells, effects) are listed, not converted; changed non-item templates are converted only for the monster actor swap and projectile-like numbers.
* **Dialogue**: only what the mod *adds*: XP rewards and trader refills. Other differences of existing infos (commands or conditions added or removed: in the Extended Mod mostly the classic-vs-Enhanced noise of its base) and **new infos** are counted and listed, not converted.
* **World**: teacher limits, container items and NPC equipment as above. Moved or new placed entities, changed routines, new layers are not translated. Templates are matched by their **entity name** (the name the engine knows them by, RE.md section 48), not by the file name: a mod whose files are renamed in its editor (the Extended Mod: `It_Axe_Ogreaxe.tple` holds the template `It_Axe_Ogre`) is converted as what it is, a change of the shipped template. A mod template that only reuses the GUID of a game template (copy and paste, 4 in the Extended Mod) is listed as a note.
* **Library and project files**: `compiled_meshes.bin`-style resource tables and every `*.bin` / `*.xxx` file the tool has no reader for are listed per kind. Animation sets are resource files and are copied as assets; their binding to a monster is done by the template patch.
* **String rows that are not about converted entities**: counted per table and not applied unless `--strings all` (a classic-based mod's tables differ from Enhanced's in hundreds of rows that are base noise, not changes).
* **Behaviour that needs scripts or hooks**: anything a mod does with game scripts (the 32-bit mod SDKs), `.dll`s, `.ini` changes and other loose files in the mod folder are listed as "other files" and not converted.

## Editor project (`--project`)

```powershell
risen-pack2mod C:\Mods\MyMod --baseline 'C:\...\Risen\data' --project 'C:\Projects\my_mod\my_mod.rmk.json'          # the project alone
risen-pack2mod C:\Mods\MyMod --baseline ... --out 'C:\...\bin\spass\mods\my_mod' --project 'C:\Projects\my_mod\my_mod.rmk.json' --verify
scripts\pack2project-check.ps1                                                                                              # the same on the Risen Extended Mod, plus the editor's validation
```

`--project FILE` writes the converted mod as a **risen-modkit project** ([editor/REQUIREMENTS.md](editor/REQUIREMENTS.md), IMP-3; file > open it in `risen-modkit`) instead of, or next to, the layer mod: `--project` alone needs no `--out`; with both, one run writes both (the project keeps its own copy of `assets/`) and `--verify` proves that they are the same mod. The project folder (the folder of FILE) holds the project file, `assets/` (the loose resources, referenced relatively), `report.md`, `pack2mod-project.json` (counts, what was not mapped, validation, verification), `NOTICE.txt` and a `.gitignore` (`*`), and `unmapped/` when something was kept as data: the same licensing rules as the layer mod, never commit it. A rerun replaces `assets/` and `unmapped/`; a folder the tool did not make (no `pack2mod-project.json`) is refused. Needs a build with the **modkit feature** (the default presets have it); a layer-only build of the tool answers `--project` with an error that says so and writes nothing.

**Design decision.** Two ways were possible: (1) write the layer mod and run the editor's importer on that folder (`mk::import_mod`), (2) map the converter's own stage tables onto the editor's `Project` model. (1) does not work: the importer reads the *editor's* data format (`data/balance.lua`, `npcs.lua`, ...), the converter writes its own (`items.lua`, `new_items.lua`, `recipes.lua` with `edit` entries on templates that are created in the same run, `patches.lua`, `dialog.lua`, requirement lists of `{ skill, amount, mode }`); making the importer read that would be a second importer for a format that has no other user. So (2): the stages are unchanged and hand the tables they write to `data/*.lua` (plus the string rows, the asset names, the changed world layers and the issue lists) to a writer (`p2m::ProjectInput`, `src/pack2mod/convert.h`); `mk::project_from_pack2mod` (`src/modkit/core/pack2project.cpp`) maps each table onto the model in a few lines per area and the project file is saved with the editor's own writer. No conversion logic is duplicated, only the shape change. `modkit_core` already links `pack2mod_core`, so the dependency is wired the other way round: `pack2mod_core` offers `p2m::set_project_writer`, `risen-pack2mod.exe` links `modkit_core` when both `SPASS_BUILD_LAYER` and `SPASS_BUILD_MODKIT` are on (`P2M_WITH_MODKIT`) and registers the writer at start; a layer-only build is unchanged (CI: the layer job and the modkit job both build). The editor's exporter and validator are used as they are: the check does not trust the mapping, it exports the project again.

What ends up where (everything the converter produces has a place; the editor grew four sections for it, [editor/USER_GUIDE.md](editor/USER_GUIDE.md) "Patches, strings, shipped dialogues and teachers"):

| Converter table | Editor project | Notes |
|---|---|---|
| `items.lua` (changed shipped items) | **Items**, *change shipped*: `value`, `damage`, `mana_cost`, requirements, modifiers, use type, category, properties; `IconImage`, `MeshFileName`, `MaterialSwitch` become the icon, mesh and material fields | the lists keep the engine's **order** and each modifier its **mode** (add, set, max, percent: `ItemDef::requirement_order`, `modifier_order`, `modifier_modes`); a requirement listed twice keeps the highest amount (all of them have to hold); an empty list stays "clear" |
| `new_items.lua` (new templates) | **Items**, *new item*: base, numbers, mesh, icon, material, properties | a new item that is a recipe item (it has an entry in `recipes.edit`) becomes one **Recipe** instead (below): the editor creates recipe items through `new_recipes` |
| `recipes.lua` `edit` | **Recipes**, *new recipe* (base = the item's clone base): station, ingredients (order kept), crafter skills, result, label, description, icon, mesh, value, other properties | a recipe item without a name or description row shows its base's (the clone's behaviour): the base's texts are written out per language (needs the game data, which `--baseline` provides) |
| `recipes.lua` `new` (shipped item turned into a recipe) | **Recipes**, *new recipe* with *give the plan once per savegame* (`learn`); `notes` names the shipped item | |
| `patches.lua` | a monster / NPC template: **NPCs**, *change shipped* (the actor `ResourceFilePath` is the mesh field); an item / recipe template: Items / Recipes; the `It_Projectile_<Spell>_S0..` templates of a shipped spell: **Spells**, *change shipped* (`damage` as one number or one per level, `projectile_properties` when every level has the same value); **everything else is a template patch of the project** (**Patches** panel, `data/patches.lua`: `risen.template.patch` on the first tick and with the live entities on every session start): `It_Cast_Light`'s range, a projectile level whose siblings' numbers are unknown | needs the game data to classify |
| `strings/*.csv` | `label` / `description` of the objects above, per language (ids are matched case-insensitively like the engine does); **every other row is a free string row** (**Strings** panel, exported into `strings/*.csv`, `\r\n` kept) | a row only in a language stays only in that language (all.csv = the first language), a new object's name table carries `default` (the layer's `set_text` serves it to the languages the table does not name: the layer mod's all.csv fallback) |
| `dialog.lua` | **Shipped dialogues**, *dialogue edits*: per shipped info an XP reward added or changed and trader refills (`chapter` of the info; chapter 1's refills also when a new game starts) | `data/dialog_edits.lua`, `risen.dialog.get` / `add_command`, once per process: the converter's own main.lua logic, now the editor runtime's |
| `world.lua` `teachers` | **Shipped dialogues**, *teacher limits* (entity ID, name, skill, limit) | `teachers` in `data/world.lua`, `risen.npc.set_teach_limit` on every world.ready |
| `world.lua` `containers` | **World**, container fills (entity id, name, layer file, items) | |
| `world.lua` `equipment` | the same fill with the *equip* mark (merged into the fill of the same entity): the export lists them in `equip` and the runtime equips them | |
| the changed `*.lrent` layers | **World**: entities that moved (by entity ID: position and yaw / pitch / roll), were removed, or were added (spawned from their creator template) | **only with `--world-edits`**, see below |
| `assets/` (resources, combat table, weather files) | **Assets**: `assets/<name>` of the project folder, kind from the file name; the combat table and `.g3ws` files are kind *other* | the export copies them byte for byte |
| `mod.toml` | **Mod**: id, name, version `0.1.0`, languages (those of the string tables, English first) | |

**Not in the project, and why** (listed in the project's `report.md`, in `pack2mod-project.json` and in the project's `editor.pack2mod.not_mapped`):

* **Moved, removed and added world entities, unless `--world-edits`.** The tool finds them (the strict layer reader of the editor, entities matched by ID; a move recomposes the mod's matrix exactly, verified), but the mod's layers are the *classic* game's files: where they differ from Enhanced's the data cannot tell the author's edits from the base's own differences. On the Risen Extended Mod: 141 entities "moved", 137 of them in NPC and monster layers (Harbour Town 59, Monastery 38, Don's camp 32, Titan dungeon 4, Gyrger 4) and 4 in event layers (one of them turned by 0.19 degrees), none removed or added; the mod's changelog names no move, 16 of the 17 layers are byte-identical in its two volumes, and the same reasoning made the 32 dialogue infos below noise. So they are counted and listed, and `--world-edits` carries them (then `--verify` recomputes every move, removal and addition from the layers). A scaled entity cannot be carried (the editor moves and turns, it does not scale).
* **New dialogue infos (24) and the 32 shipped infos that differ in conditions / commands** are the classic game's own differences too: the 32 remove Enhanced's bug fixes (`PALLAS_BUGFIX` game events, `CloseQuest` commands, quest conditions, the `Illumar_SellsScrolls` typo restored; EXTENDED_MOD_ANALYSIS.md), the 24 are the QA test conversations of three test NPCs (`QATEST_*`, owners `Dipsy`, `Lala`, `Tinky`) that Enhanced removed; their `Say` commands carry no text (the text id is not in the record) and the game's `infos.tab` already holds the QA rows. Nothing in the data says the author meant any of them, and the lines cannot be written without their texts. They are counted in the report's *Not converted*.
* **New NPC templates** (and other non-item templates): the Extended Mod has none, so there is no data to verify a conversion against; they stay listed as not converted (`needs = tool`) instead of being guessed.
* **Modifier modes the engine does not have, and non-whole numbers.** The engine's skill amounts are integers (`gCSkillValue.Amount` is a long; the layer refuses anything else: `the amount must be an integer`) and its modes are add / set / max / percent (`gESkillModifier_*`), so a converted mod cannot contain others; if one did, the entry would be reported with the reason (unit test).
* A modifier listed twice for one skill (one map entry per skill) or requirements / modifiers on a recipe item (a recipe has no such fields): reported (none in the Extended Mod).

**Verification** (`--verify`, needs `--out` and `--project`). The project is exported with the editor's exporter into a temporary folder and compared with the layer mod of the same run (`mk::compare_mod_with_export`): the **effective settings of every template** (the layer's own aliases normalised: `value` is `gCItem_PS.GoldValue`, `mesh` is `eCMesh_PS.MeshFileName`, requirement and modifier lists **in their order with their modes**, a spell's projectile edit expanded to its projectile templates, the patches), the **recipes** (station, ingredients in order, skills, result), the **texts** per language (inline names of the export with their `default`, `strings/*.csv`, the fallback as the layer resolves it; CRLF read as LF because the converter writes its CSV with CRLF also inside quoted texts), the **container fills with their equip marks**, the **dialogue edits** per info (XP added / changed, refills, chapter), the **teaching limits** and every **asset file** (names and bytes). The world edits have no counterpart in the layer mod: they are recomputed from the layers (a move recomposes the mod's matrix, a removal is an entity the mod's layer lacks, a spawn sits where a new entity is). On the Risen Extended Mod: 1570 settings of 367 templates, 2245 texts, 14 fills, 178 dialogue operations (67 XP rewards added, 2 changed, 105 refills, 4 chapters), 9 teaching limits and 334 assets compared, equal; with `--world-edits` also the 141 moves; the project has 286 items, 51 recipes, 26 NPC templates, 1 spell edit, 1 template patch, 14 container fills, 69 dialogue edits, 9 teaching limits, 50 free string rows and 334 assets; the editor's validation with the game data: 0 errors, warnings only for stock textures and actors the mod replaces under the same name (145 + the combat table and the weather file) and 3 items without a label row of the mod. A difference makes the tool exit 1 (project and report are kept) with the first difference in the message and all of them in the report. **Live:** the editor runtime's patches, dialogue edits, teaching limits, ordered modifier lists with modes, string rows and `default` texts run in the game (scenario `extras`, 14 checks; `scripts\pack2project-live.ps1` loads the Extended Mod's whole project export).

Known differences that are not errors: the converter's own CSV writer turns a table's `\r\n` into `\r\r\n` (the project keeps `\r\n`, the comparison reads both as `\n`), and a project made without `--baseline` game data cannot classify template patches (they become template patches) or copy a recipe item's base texts.

## Profiles

A profile is JSON with knowledge about **one specific mod** that cannot be derived from its archives: which of two volumes is the changelog state, which string rows are real changes and which spreadsheet noise, which of the author's recipes name templates that do not exist and what they obviously meant, how the loose files group for switching. `tools\pack2mod\profiles\risen_extended.json` is the profile of the Risen Extended Mod (facts about the mod's own mistakes and which string rows matter; no content of the mod). Keys: `id`, `name`, `recipe_fixes.result` / `.ingredient`, `strings.only_rows` (table -> the only rows applied), `strings.changed_with_changelog_combat`, `strings.changed_all`, `asset_groups` (`prefix`, `exclude_prefix`), `combat_about`, `weather_group`. Without a profile the tool is fully generic and reports the same problems as `unconverted`.

## Tests

* **Unit tests** (`spass_tests`, `tests/pack2mod_tests.inc`, no game data): archive writer / reader round trip (compressed, stored, empty members, directories, damaged archives), string tables, a template builder and the scanner (properties, enums, arrays, GUID references), the lossless combat table round trip, text helpers, Lua / JSON emitters (layout identical to `tools/extmod_gen.py`), the JSON reader, and an **end-to-end conversion** of synthetic archives (changed item, new item with its base, identical file skipped, strings with artefacts, assets, layering of three volumes, refusal to write into foreign folders or the game, determinism, `--list`, `--dry-run`).
* **Golden test** (`scripts\pack2mod-golden.ps1 [-Combat changelog|shipped|off]`, needs the mod and the game): runs the C++ tool and the Python oracle `tools/extmod_gen.py` (which stays in the repository for exactly this) on `B:\TMP\Risen_Extended_Mod` against `B:\DevDrive\risen-test\data` and compares with `tools/pack2mod_golden.py`: 353 files identical (all `data/*.lua`, 5 string files, `features.json`, the 332 assets and the combat table / weather variants byte by byte, `main.lua`, `config.lua`), the manifest counts, statistics, unconverted entries and warnings. One explained difference remains in `data/world.lua` (the Python generator reads a research file that was made with name-keyed lookups): the tool finds a **second chest** with the same name in `BD_Farm_Events.lrent` (entity id `28e2d7f0-...`: `It_Po_EXP_Special`, `It_BlackPearl`). (Until phase F there was a second one, Karakos' `It_Axe_Ogreaxe`: a file name artefact, templates are known by their entity name, RE.md section 48.) Everything else (200 changed items, 132 new items, 46 + 5 recipe items, 30 patches, 69 XP infos, 105 trader entries, 9 teacher limits, 3 equipment items, 332 assets, 5 languages) is identical.
* **Editor project** (`modkit_tests`, `tests/modkit/pack2project_tests.inc`, made-up tables and archives, no game data): the mapping of every table (requirement lists, the lifted icon / material, recipe items, the Frost projectiles as one spell, equipment merged into a fill, case-insensitive texts, unmapped entries), the export of the mapped project against the layer mod written from the same tables (equal, and a changed number / ingredient / text / fill / asset byte is found), and the command line on synthetic archives (project alone, both outputs with `--verify`, rerun, refusal of foreign and game folders, the error of a build without the editor). `scripts\pack2project-check.ps1` runs the real mod (it skips cleanly when the mod or the game data is missing). `tests/pack2mod_tests.inc` checks the error of a layer-only build.
* **Live check**: the tool's output installed as `mods/risen_extended` passes the scenarios `extmod` (32 checks, two game processes) and `extplay` (13 checks) unchanged: `scripts\smoke-test.ps1 -Scenario extmod,extplay -Parallel 2`. (`check.lua` and `play.lua` of `tools/extmod_templates/` are test files of that mod and are copied in by hand; a generated mod does not contain them.)

## How it fits together

```
risen-pack2mod  ->  <mod>\mod.toml, main.lua, config.lua      the mod (generic code, embedded)
                    <mod>\data\*.lua                          the numbers (only differences)
                    <mod>\strings\*.csv                       the texts
                    <mod>\assets\*                            loose resources (flat, original names)
                    <mod>\variants\, features.json            switchable files
                    <mod>\manifest.json, report.md            what was done and what was not
```

The generated `main.lua` is the same generic code for every mod: it applies the data stages in the order *new templates, item changes, recipes, patches* on the first `tick` and on every `session.start`, the dialogue edits once per process, the world edits once per savegame, the teacher limits on every `world.ready`. A bad entry is logged (`<id>: ...`) and counted, never fatal; `config.lua` switches the groups.

Formats the tool reads and writes are in [RE.md](RE.md) sections 43 (archives, templates, string tables, library files) and 47 (what the converter learned: world layer entities, GUID collisions, chapter infos); the Python readers `tools/g3pak.py`, `g3tple.py`, `g3tab.py`, `g3cs.py` and the generator `tools/extmod_gen.py` remain as the test oracle.

## Limits

Measured on the Risen Extended Mod: 7 s for the whole conversion (the archives are 105 MB), 102 MB of assets. The template scanner is tolerant, not a full parser: a property of a type it does not know is carried as hex and reported (`enum value ... has no known name`) rather than guessed. Enum names exist only for the enums item templates use (`src/pack2mod/enums_data.inc`); a mod that changes other enums gets `unconverted` entries with `needs = tool` until the table is extended (`tools/extmod_enums.py` learns more from a game run of `mods/itemdump`). Archives of kinds other than `common` and `compiled` (sound and speech volumes, GUI packs) are not read.
